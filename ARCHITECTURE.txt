PIK-CHA! SYSTEM ARCHITECTURE
=============================
(DIY 네컷 포토부스 - 학교 EXPO용)


1. 시스템 개요
--------------
전체 시스템은 서로 독립적으로 배포/실행되는 두 개의 하위 시스템과, 둘이 공유하는
AWS 백엔드(API Gateway + Lambda + DynamoDB + S3)로 구성된다.

  [A] 부스 파이프라인 (booth pipeline)
      - 물리적으로 부스 PC(+ 프린터 연결 PC) 위에서만 실행
      - 캐논 DSLR로 촬영 -> 프레임 합성 -> S3 업로드 -> 인쇄 -> SMS 발송
      - AWS 자격증명을 전혀 안 가짐 (학교 정책상 IAM 액세스키 발급 불가) - 전부
        API Gateway 뒤의 Lambda(IAM Role 보유)를 거쳐서만 AWS와 통신

  [B] 웨이팅 시스템 (waitlist system)
      - S3 정적 웹사이트로 호스팅된 6개 페이지 - 아무 브라우저에서나 접속 가능
      - 부스 PC와 완전히 분리되어 동작, API Gateway를 브라우저에서 직접 호출
      - 손님 등록 -> 순번 발급 -> 대기 -> (부스에서 순번 입력) -> 자동 다음팀 호출

두 시스템을 잇는 유일한 연결고리는 "ticket_number" 하나 - 손님이 웨이팅 시스템에서
받은 순번을 부스 키오스크 화면에 직접 입력하는 것으로 두 시스템이 연결된다.


2. 구성 요소
------------

[부스 PC]
  camera/app.py            FastAPI 백엔드 (포트 8000). 카메라 제어, 라이브뷰
                            스트리밍(WebSocket), 촬영 시퀀스 실행, 프레임 합성,
                            S3 업로드 트리거.
  camera/edsdk_wrapper/     캐논 EDSDK ctypes 래퍼 (초기화/세션/셔터/라이브뷰).
  camera/edsdk_worker.py    EDSDK 명령을 전용 스레드 하나로만 직렬화하는 워커
                            (EDSDK가 세션 연 스레드에서만 명령을 받아야 하는 제약 때문).
  camera/aws_uploader.py    AWS 연동 경계 - API Gateway만 호출, boto3/자격증명 없음.
  frontend/                 정적 HTML/JS/CSS 키오스크 UI (포트 5500, 별도 정적서버).
                            Main -> Number_of_Prints -> Personal_Info(순번입력) ->
                            CountDown -> Take_a_Picture -> Review_Photos ->
                            Select_Frame -> Print_Photo 순서로 흐름.

[프린터 PC] (부스 PC와 같을 수도, 다를 수도 있음)
  printer/print_worker.py  API Gateway를 5초 간격으로 폴링해서 인쇄 대기열을
                            처리하는 상주 프로세스. Windows GDI로 프린터에 직접
                            그려서 인쇄(인쇄 대화상자 없음). 인쇄매수(quantity)만큼
                            반복 인쇄 후, 프린터 스풀 큐가 완전히 빌 때까지 대기한
                            뒤 완료 보고.

[S3 정적 호스팅 - 웨이팅 시스템 프론트]
  admin/WaitingList_UserPage           손님 등록 폼 (학과/학번/이름/전화/인원수)
  admin/WaitingList_UserPage_Status    발급받은 순번으로 개인 대기상태/인화상태 조회
  admin/WaitingList_AdminTablet        공개 태블릿 디스플레이 - "현재 O번 입장중"만 표시
  admin/WaitingList_AdminPage          관리자 대시보드 (현재 대기팀 수)
  admin/WaitingList_AdminManage        관리자 - 웨이팅리스트 목록/취소 관리 (Basic Auth)
  admin/PrintStatus_AdminManage        관리자 - 인화현황 조회/재인쇄/SMS재발송 (Basic Auth)

[AWS - API Gateway + Lambda] (Lambda/ 폴더에 소스, 수동 배포)
  sgu-pikcha-presign          S3 presigned PUT/GET URL 발급. 세션 아이템에
                              name/phoneNumber/printQuantity 선기록.
  sgu-pikcha-session-logger   *API Gateway 아님* - S3 업로드 이벤트로 트리거됨.
                              세션 기록 확정 + 인쇄 대기열(__PENDING_PRINTS__)에 job 등록.
  sgu-pikcha-print            인쇄 워커용 폴링 API + 인쇄완료 시 SMS 자동발송.
  sgu-pikcha-admin            Basic Auth 관리자 API - 조회/재인쇄/SMS재발송/웨이팅관리.
  sgu-pikcha-waitlist         웨이팅 순번 발급/조회/취소/자동호출 API.

[AWS - 데이터 저장소]
  DynamoDB: sgu-pikcha-photobooth-sessions
      - session_id 로 키. 세션별 name/phoneNumber/printQuantity/printStatus/sms_sent 등.
      - 예약 싱글턴 아이템: __PENDING_PRINTS__ (인쇄 대기열), __STATS__ (누적 통계)
  DynamoDB: sgu-pikcha-waitinglist
      - ticket_number 로 키. status/department/student_id/name/phone_number/party_size 등.
      - 예약 싱글턴 아이템: ticket_number=0 (counter, now_serving 보유)
  S3 버킷
      - sessions/{session_id}/ 아래 컷 4장 + 합성본 저장

[외부 서비스]
  SOLAPI (문자 발송 API) - HMAC-SHA256 서명 인증, sgu-pikcha-print/sgu-pikcha-admin이 호출


3. 데이터 흐름 - 부스 촬영 세션 (한 손님 기준)
----------------------------------------------
 1. (사전) 손님이 웨이팅 시스템(S3)에서 등록 -> ticket_number 발급받음
 2. 부스 키오스크 Personal_Info 화면에 ticket_number 입력
      -> camera/app.py -> sgu-pikcha-waitlist(/waitlist/start-session)
      -> 학과/학번/이름/전화번호 반환, 티켓 status: waiting/called -> in_session
 3. CountDown -> Take_a_Picture: /api/four-cut/start (ticket_number 포함)
      -> 목업 또는 실카메라로 N컷 촬영, WebSocket으로 진행상황 브로드캐스트
      -> 촬영 종료(성공/실패 무관) 시 sgu-pikcha-waitlist(/waitlist/advance) 호출
         -> 이 티켓 status: photographed, 다음 waiting 티켓을 called로, now_serving 갱신
 4. Review_Photos -> Select_Frame: 사진 선택 + 프레임/로고/색 Canvas 합성
      -> /api/fourcut/create-composited (name/phone/print_quantity 포함)
      -> aws_uploader.upload_fourcut_session()
 5. sgu-pikcha-presign: presigned PUT URL 발급 + name/phoneNumber/printQuantity 선기록
 6. 컷 4장 + 합성본 S3 업로드 (presigned URL로 직접 PUT)
 7. S3 업로드 이벤트 -> sgu-pikcha-session-logger 자동 트리거
      -> 세션 레코드 확정, __STATS__ 갱신, __PENDING_PRINTS__ 에 인쇄 job 등록
 8. Print_Photo 화면: QR 코드 표시, 30초 후 자동으로 Main 복귀
 9. printer/print_worker.py 가 폴링 중 job 발견
      -> sgu-pikcha-print(/print-jobs)로 다운로드 URL+매수 수신
      -> 이미지 다운로드 -> GDI로 매수만큼 인쇄 -> 프린터 큐 완전히 빌 때까지 대기
      -> sgu-pikcha-print(/print-complete) 보고
10. sgu-pikcha-print: printStatus=printed 기록 + 전화번호로 SMS 자동 발송(SOLAPI)


4. 데이터 흐름 - 웨이팅 순번 생애주기
--------------------------------------
  waiting --(부스에서 ticket_number 입력, start-session)--> in_session
  waiting --(관리자 취소 or 유저 취소, cancel)--> canceled
  waiting --(다른 팀 촬영 종료 시 advance가 자동 호출)--> called (순서 무관, 표시용)
  in_session --(촬영 종료, advance)--> photographed
  (photographed 이후 인화/SMS 상태는 세션 테이블 쪽 printStatus/sms_sent로 추적,
   웨이팅 테이블 자체엔 "completed" 로의 자동 전이는 구현되어 있지 않음)

  ticket_number 발급은 DynamoDB 원자적 카운터(ticket_number=0 아이템의 counter
  필드를 ADD)로 처리 - 동시 등록에도 번호 중복 없음(실패 시 번호 하나 건너뛸 뿐).
  번호는 행사 4일 내내 이어짐 (일별 리셋 없음).


5. 배포 토폴로지
-----------------
  부스 PC        : camera/app.py (8000) + frontend/ 정적서버(5500) + 브라우저(키오스크)
  프린터 PC       : printer/print_worker.py (부스 PC와 동일 PC일 수도 있음)
  AWS API Gateway : sgu-pikcha-presign/print/admin/waitlist 4개 Lambda 라우팅
  AWS S3 (버킷 1) : 촬영 사진 저장 + 업로드 이벤트로 session-logger 트리거
  AWS S3 (버킷 2) : admin/ 6개 페이지 정적 웹사이트 호스팅
  DynamoDB        : 2개 테이블 (sessions, waitinglist)
  손님 기기/태블릿  : 브라우저로 S3 정적사이트 접속 (등록/조회/태블릿 디스플레이)
  관리자 기기      : 브라우저로 S3 관리자 페이지 접속 + Basic Auth


6. 핵심 설계 결정 / 주의사항
------------------------------
- 부스 PC는 AWS 자격증명을 절대 안 가진다 -> 모든 AWS 접근은 API Gateway+Lambda 경유
- EDSDK는 세션 연 스레드에서만 명령 가능 -> 전용 워커 스레드 1개로 직렬화
- 카메라/DLL 없어도 항상 동작 -> 목업 촬영 분기가 영구 폴백으로 존재 (제거 대상 아님)
- 웨이팅 순번 진입 순서는 강제하지 않음 -> now_serving은 표시용, 검증용 아님
- 인쇄완료 판정은 고정 대기시간이 아니라 실제 프린터 스풀 큐가 비는 것을 감시
- API Gateway 라우트 추가 시 "Lambda 프록시 통합" 체크 + "배포(Deploy)" 둘 다 필수
  (둘 중 하나만 빠져도 200을 반환하며 조용히 실패하는 경우가 있었음)
